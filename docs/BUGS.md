## BUG-0010 · 10.08.2026 · Без JS страница 404 показывала три заголовка H1 · закрыт

**Найдено** полировочным проходом по всем страницам.

**Воспроизведение.** JavaScript отключён, открыт несуществующий адрес.
На странице оставались все три языковые версии сразу — три `<h1>` подряд,
три разных языка в одном документе, структура для скринридера сломана.

**Первопричина.** Разметка содержала все три версии, а выбор нужной делал
скрипт удалением лишних. Без скрипта удалять было некому. Ошибка в том,
что состояние «по умолчанию» задавалось не разметкой, а работой JS.

**Лечение.** По умолчанию видна одна версия — ивритская, язык сайта
по умолчанию; остальные помечены `hidden`. Скрипт показывает подходящую
и удаляет прочие. Теперь без JS остаётся ровно одна версия и один `H1`.

**Подтверждение.** Полировка по всем страницам: 417 проверок, 0 провалов.

### Две сопутствующие ошибки измерения (в проверке, не в коде)

1. Проверка считала `h1` без учёта видимости и объявляла нарушением скрытые
   заголовки, которых нет ни в дереве доступности, ни на экране.
2. Проверка запрашивала `404.html` по адресу без расширения, получала от сервера
   404 и измеряла пустую страницу вместо самой страницы.

Оба случая — тот же класс, что и раньше: **доказательство обязано измерять то,
что утверждается** (QUALITY_DOCTRINE §6). Проверки исправлены; страница
под проверку не подгонялась.

## BUG-0009 · 10.08.2026 · Кнопка не пробрасывала data-атрибуты, форма была мертва · закрыт

**Найдено** при первой проверке формы на живой странице.

**Воспроизведение.** `<Button type="submit" data-submit>` рендерился без
`data-submit`. Скрипт формы искал собственную кнопку по этому атрибуту,
не находил и падал на первой же строке — форма не отправлялась вообще,
кнопка «отправить ещё» не работала, и в консоли было тихо ровно до момента,
когда кто-то попробует нажать.

**Первопричина.** Компонент `Button` разбирал только известные ему пропсы
и не имел rest-спреда. Любой атрибут, не перечисленный в интерфейсе, молча
исчезал. Это класс, а не единичный случай: то же произошло бы с `id`,
`aria-*` и любым другим крючком.

**Лечение.** Rest-спред на элемент + типы для `data-*` и `aria-*` в пропсах.

**Подтверждение.** Полный сценарий формы на живой странице: заполнение →
отправка → экран благодарности → «отправить ещё» возвращает форму;
ошибок в консоли ноль.

**Заодно исправлено поведение, которое дефектом не считалось.** Отправка
раньше порога 2.5 с показывала человеку сообщение о сбое сервера. У живого
пользователя это бывает при автозаполнении. Теперь форма молча ждёт
недостающие миллисекунды и отправляет; а заполненная ловушка показывает боту
обычную благодарность — сообщать ему, что он распознан, незачем.

## BUG-0008 · 10.08.2026 · Закрытые подсказки расширяли документ · закрыт

**Найдено** полировочным проходом: на 320px `scrollWidth` 349 при `clientWidth` 320,
хотя ни одна подсказка не была открыта.

**Первопричина.** Пузырь скрывался `visibility: hidden`. Такой элемент остаётся
в раскладке и продолжает расширять прокручиваемую область — три закрытых пузыря
выносили документ за край экрана. Скрытие видимостью не равно отсутствию.

**Лечение.** Закрытое состояние — `display: none`; открытое — `display: block`
плюс скрипт-кламп, который держит пузырь внутри вьюпорта (чистым CSS элемент
не знает, где край экрана). Заодно снят fade: анимация здесь ничего не давала,
а при `display` требовала бы дополнительных ухищрений.

**Почему это не сломало доступность.** По спецификации вычисления имени
и описания текст элемента, на который ссылается `aria-describedby` или
`aria-labelledby`, используется независимо от его видимости.

**Подтверждение.** `npm run polish:ui` → `320px · витрина без горизонтальной
прокрутки — scrollWidth 320 ≤ clientWidth 320`, 25/25.

### Сопутствующая ошибка в моей же проверке

Первый прогон аудита объявил восемь полей формы «без доступного имени».
Это была ошибка проверки: алгоритм не учитывал `<label for>` и обрамляющий
`<label>`, которыми скринридер как раз и называет поле. Разметка была корректной.
Проверка исправлена — иначе она заставляла бы «чинить» правильный код.

## BUG-0006 · 09.08.2026 · Две локали из трёх молча пропадали из коллекции · закрыт

**Найдено** снимком витрины: заголовки локалей отрисовались, карточек под ними
не было ни одной. Сборка при этом была зелёной.

**Воспроизведение.** Две работы × три языка = шесть записей. `getCollection('works')`
возвращал **две**: `pergola-lamelnaya-nof-hagalil` и `zabor-kombi-migdal-haemek`.

**Первопричина.** Loader `glob` по умолчанию берёт `id` записи из поля `slug`
фронтматтера, если оно есть. А `slug` у трёх языковых версий одной работы общий
по определению — это URL, он обязан совпадать. Записи с одинаковым `id`
схлопывались в одну, и две версии из трёх исчезали.

Схема этого поймать не могла: каждая запись по отдельности была валидна.
Проверка целостности между записями просто не существовала.

**Лечение** (первопричина, не симптом). `generateId` строит `id` из пути файла:
`work-01-pergola/ru`. Плюс заведена проверка `check:content`, которой раньше
не было: у каждой работы обязаны быть все три версии, `id` и `slug` обязаны
совпадать между языками, один `slug` не может принадлежать двум работам.

**Подтверждение.** Все шесть записей в коллекции; карточки рендерятся на трёх
языках — `docs/evidence/f2/works-from-content-light.png`.
Негативный тест: удаление `he.mdx` роняет `check:content` (самотест 21/21).

**Урок.** Зелёная сборка и валидная схема не означают, что данные на месте.
Отсутствие записи выглядит как пустой список, а пустой список выглядит как
«ещё не наполнили». Поймал снимок, а не проверка, — поэтому проверка заведена.

## BUG-0007 · 09.08.2026 · У работы не было заголовка, материал показывался кодом · закрыт

**Найдено** тем же снимком витрины.

**Воспроизведение.** На карточке вместо названия работы стояло первое предложение
описания, а тег материала показывал `WOOD` и `COMBO` — сырые значения enum,
одинаковые на всех трёх языках.

**Первопричина.** Два разных недосмотра одного корня — схема писалась под
фикстуру, а не под паспорт:
1. `docs/INTAKE_TEMPLATE.md` спрашивает «рабочее название», но поля `title`
   в схеме не было. Карточка вынужденно резала описание по первой точке.
2. Материал хранится кодом (`wood`/`metal`/`combo`) — это правильно, коды
   не переводятся. Но словаря для их показа не существовало, и код утекал в UI.

**Лечение.** Добавлено обязательное поле `title` в схему и во все демо-паспорта;
в словарь добавлен неймспейс `materials`, витрина показывает материал через него.

**Подтверждение.** Теги: `Алюминий | עץ | Комбо | Дерево | משולב | Combo | Wood`.
Заголовки RU: «Пергола с ламелями во дворе», «Забор с просветами вдоль улицы».

**Это ровно тот риск, который записан в манифесте 03** («схема под фикстуру,
а не под жизнь»). Сработал он на демо-паспортах, а не через месяц на реальных —
то есть дёшево. Возврат к шагу 2 при реальных паспортах остаётся штатным.

## BUG-0005 · 08.08.2026 · В RTL метрика «100×50» отображалась как «50×100» · закрыт

**Найдено** на скриншоте витрины при шаге 4 F1 — сравнением LTR- и RTL-панелей
одного и того же компонента.

**Воспроизведение.** Карточка-«паспорт объекта» в RTL-панели: профиль,
переданный как `100×50`, показан как `50×100`; площадь `18 м²` — как `м² 18`.

**Первопричина.** Символ `×` (U+00D7) относится к нейтральным (ON). В абзаце
с RTL-направлением алгоритм bidi по правилам N1/N2 разрешает нейтраль в
направление абзаца, из-за чего строка распадается на два числовых прогона,
и они выкладываются справа налево. То есть значение меняло **смысл**, а не
только вид: «профиль 100×50» и «профиль 50×100» — разные изделия.

**Лечение.** Значение метрики и год обёрнуты в `<bdi dir="ltr">` — изолированный
LTR-прогон. Это ровно то, что требует бриф §2 («телефоны и числа в иврите —
`dir="ltr"`»), применённое к измерениям. Выравнивание блока при этом остаётся
по началу строки RTL — изолируется только внутренний порядок.

**Подтверждение — визуальное, а не текстовое.** Первая моя проверка читала
`textContent` и показывала «100×50» — но `textContent` возвращает порядок DOM
и был бы таким же и до фикса. Годное доказательство — снимок:
`docs/evidence/f1/card-rtl.png`, где RTL-карточка показывает «100×50» и «18 м²».
Вывод про негодные доказательства внесён в QUALITY_DOCTRINE §6.

**Зона риска на будущее.** Тот же класс дефекта ждёт любые технические значения
в RTL: размеры `4×3`, диапазоны `2–3 дня`, версии, координаты, диаметры болтов
(`M12`). В F2 это должно стать правилом схемы, а не ручной обёрткой в каждом месте.

## BUG-0004 · 07.08.2026 · `process` в astro.config без типов Node уронил CI · закрыт

**Воспроизведение.** `npm run check:types` → `astro.config.mjs:28 ts(2591):
Cannot find name 'process'`. Появилось вместе с флагом витрины
`const SHOWCASE = process.env.UI_SHOWCASE === '1'` (DEC-0011).

**Первопричина.** В проекте не было `@types/node`, а `astro check` типизирует
и файлы конфигурации. Ошибка настоящая, не ложная: без типов Node любое обращение
к `process` в конфиге не проверяется.

**Лечение.** `npm i -D @types/node` — ровно то, что предлагает сам компилятор.
Подавлять `@ts-ignore` было бы хитростью по §2 и уронило бы `check:markers`.

**Подтверждение.** `npm run check:types` → 0 errors / 0 warnings / 0 hints, exit=0.

### Сопутствующая ошибка процесса (важнее самого бага)

Локально я прогнал проверки через `grep -E "errors|warnings|hints"` и увидел
«0 warnings / 0 hints». Строка `- 1 error` — **в единственном числе** — под шаблон
не попала, а код возврата съел пайп. В манифест 02 ушло «`npm run check` зелёный»,
чего на тот момент не было. Поймал это CI, а не я.

**Вывод, действующий дальше:** результат проверки определяется кодом возврата,
а не глазами в отфильтрованном выводе. Фильтровать вывод можно только после того,
как зафиксирован exit code. Запись в манифесте 02 исправлена.

## BUG-0002 · 07.08.2026 · Тёмная тема не работала без JavaScript · закрыт

**Найдено** полировочным проходом F0 (QUALITY_DOCTRINE §4, пункт «отключённый JS»).

**Воспроизведение.** Браузер с системной тёмной темой, JavaScript отключён →
страница открывается светлой. Ожидание брифа §2: каскад
localStorage → prefers-color-scheme → light.

**Первопричина.** Тёмные значения токенов были объявлены **только** в блоке
`[data-theme='dark']`, а этот атрибут проставляет inline-скрипт. Нет JS —
нет атрибута — нет тёмной темы. То есть вторая ступень каскада
(системная настройка) существовала лишь как побочный эффект работы скрипта,
а не как самостоятельное правило.

**Лечение** (первопричина, не симптом). `src/styles/variables.css` перестроен:
значения каждой палитры записаны ровно один раз как `--light-*` / `--dark-*`,
а рабочие имена присваиваются тремя ступенями — `:root` (светлая),
`@media (prefers-color-scheme: dark)` (системная, без JS),
`[data-theme]` (явный выбор, идёт последним и перебивает). Добавлен `color-scheme`,
чтобы браузер красил скроллбары и системные контролы в тон.

**Подтверждение.** `npm run polish`:
```
✓ без JS · системная light → фон rgb(247, 247, 249), color-scheme light
✓ без JS · системная dark  → фон rgb(18, 20, 23),   color-scheme dark
```
Поведение с включённым JS не изменилось — `npm run gate:f0` по-прежнему 45/45.

## BUG-0003 · 07.08.2026 · Длинная строка без пробелов растягивала документ · закрыт

**Найдено** полировочным проходом F0 (пункт «очень длинные строки»).

**Воспроизведение.** Вьюпорт 320px, в заголовок попадает 120 символов без
пробелов (реальные кандидаты: URL, длинное название населённого пункта,
склеенный адрес) → `scrollWidth` 1347 при `clientWidth` 320, появляется
горизонтальная прокрутка всей страницы.

**Первопричина.** В базовых стилях не задано поведение переноса неразрывных
последовательностей. По умолчанию строка не переносится и раздвигает блок,
а вместе с ним и документ.

**Лечение.** `overflow-wrap: break-word` в базовом слое на `body` — то есть
для всего контента разом, а не точечно для того элемента, где это заметили.

**Подтверждение.** `npm run polish`:
```
✓ 320px · длинная строка без пробелов не ломает раскладку — scrollWidth 320 ≤ 320
```
