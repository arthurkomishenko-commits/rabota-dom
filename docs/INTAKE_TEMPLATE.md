# INTAKE_TEMPLATE.md — Паспорт работы (шаблон сбора)
Размещение: `docs/INTAKE_TEMPLATE.md` · Один заполненный экземпляр = одна работа. Поля соответствуют схеме контента 1:1. Для запуска нужно ≥8 полных паспортов (гейт F8); для старта разработки достаточно первых 2–3.

## Как собирать (Артур)

На каждую работу — **одна папка**: внутри фото и файл `intake.md` (копия блока ниже, заполненная). Неполный паспорт не публикуется — это гейт схемы; поле без данных лучше оставить пустым, чем выдумать.

### Путь в репозитории — согласован 08.08.2026 (DEC-0013)

```
content/works/work-NN/
  intake.md          ← этот шаблон, заполненный. НЕ публикуется
  photos/
    cover.jpg
    process-01.jpg
    node-01.jpg
  he.mdx  ru.mdx  en.mdx   ← записи коллекции, их пишет Claude Code по intake.md
```

**Твоя часть — только `intake.md` и `photos/`.** Записи `*.mdx` появляются позже: их собирает Claude Code из паспорта, они проходят Zod-гейт и EDITORIAL.

**Почему `content/` в корне, а не `src/assets/raw/`** (твоё исходное предложение).
Идея «одна папка на объект, внутри `intake.md`» принята целиком — изменено только место:

1. `src/assets/` — это пространство, из которого Astro берёт картинки при импорте. Сырьё там соседствует с тем, что реально уезжает на сайт: легко случайно импортировать в страницу оригинал на несколько мегабайт, и проверка бюджетов не сможет отличить «вход пайплайна» от «то, что грузит посетитель».
2. В Astro 7 контент больше не обязан лежать в `src/content/`: loader `glob` берёт `base` от корня проекта. Значит паспорт, фото и записи можно держать в одной папке — ровно той единицей, которой ты и собираешь.
3. Производные (WebP/AVIF нужных размеров) в репозиторий не попадают вообще — они создаются при сборке и живут только в `dist/`. Репозиторий не растёт оптимизированными копиями (гейт F9).

### Требования к файлам, которые кладутся в `photos/`
- Длинная сторона **≥1600px** и **≤2400px**, вес одного файла **≤1.5 МБ**.
  Это осознанная граница: ниже 1600 не хватит на retina-карточку, выше 2400 в репозитории лежит мёртвый вес — всё равно ужимается при сборке.
- Присылать «как файл/документ», не «как фото»: мессенджер иначе пережимает.
- Проверяется машинно: `npm run check:budgets` (папка `content/works/**` добавляется в проверку в F2). Превышение — красная сборка, а не «потом поправим».

- **Точка для карты:** улица или перекрёсток РЯДОМ с объектом, не дом клиента. Google Maps → долгий тап на улице → скопировать координаты. Система дополнительно огрубит и сместит их.
- **Отзыв клиента (если есть):** имя · 1–3 предложения его словами · ☐ клиент согласен на публикацию отзыва

### Фото к работе (минимум: cover + 2, из них ≥1 процесс или до/после)
- ☐ **Cover** — горизонтальный, фронтально, общий вид

- ☐ Узлы крупным планом — стык, кронштейн, крепление (очень желательно: это главное доказательство мастерства)

## Критерии отбора АРХИВНЫХ фото (жёсткие)
- Только собственные съёмки Вовы. Никаких сохранённых из интернета, чужих сайтов, поиска картинок — даже «для примера». Вотермарка = сразу нет.
- Резкое, не пережатое мессенджерами до мыла (лучше «отправить как файл/документ», не как фото).
- В кадре нет: мусора, открытых банок, инструмента враскидку, людей, не давших согласия, номеров машин крупно.
- Длинная сторона ≥1600px. Вертикальные годятся для процесса, cover — горизонтальный.

## Мини-ТЗ для НОВЫХ съёмок (когда Вова снимает специально)
Объектив 1x (не 0.5x — гнёт столбы) · камера на уровне груди, фронтально · узлы — макро с 10–20 см · дерево — час после рассвета или до заката, алюминий — лёгкая облачность · «до/после» — с одной точки (пометить место) · рабочая зона выметена · бонус-кадр: уровень на балке, фокус на пузырьке.
